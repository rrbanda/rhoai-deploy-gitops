THE LANDSCAPE

What Makes RHOAI Unique

RHOAI is not a single operator — it’s an ecosystem of 14 operators, dozens of CRDs, version-locked dependencies, and precise ordering requirements. Managing this at scale calls for automation.

Complexity
14 Operators, 50+ CRDs
RHOAI depends on cert-manager, ServiceMesh, Kuadrant, Kueue, NFD, and more. Each has its own namespace, subscription channel, and version constraints. Miss one and the DSC never reconciles.
Ordering
CRDs Before CRs
Custom Resources need their CRDs to exist first. With 14 operators installing CRDs at different speeds, ordering matters. Automation ensures CRDs land before CRs.
Drift
Configuration Drift
Namespaces change, secrets get overwritten, operators drift to newer channels. Continuous reconciliation detects and corrects drift automatically.

The opportunity: With this many moving parts, automation isn’t optional — it’s the path to reproducible, auditable, self-healing deployments across every cluster.

PATTERN

The App-of-Apps Pattern

4 ApplicationSets auto-discover directories. Add a dir, push, ArgoCD creates the Application.

"This is the App-of-Apps pattern — and it's what makes the entire system extensible without touching any ArgoCD configuration." "One oc apply creates the ArgoCD instance. ArgoCD picks up the 4 ApplicationSets. Each ApplicationSet uses a Git directory generator — it scans a path in the repo and creates one ArgoCD Application per subdirectory it finds." "Look at the numbers. cluster-operators scans 12 directories, creates 11 apps — one directory is excluded. cluster-instances scans 24 directories, creates 17 — some are excluded because their CRDs don't ship yet in EA2. cluster-models and cluster-services are opt-in, wave 5." "The two standalone apps are special. rhoai-dsc at wave 3 uses a Replace sync strategy with ignoreDifferences on the DSC status — because the RHOAI operator constantly mutates the status field and ArgoCD would fight it otherwise. PHASE 4

Bootstrap: 7 Layers in One Command

oc apply -k bootstrap/overlays/default — after this, Git is the only interface.

  1. GitOps Operator — Subscription + ClusterRoleBinding
  2. ArgoCD Instance — Helm + Kustomize enabled, health checks for DSC/DSCI CRDs
  3. cluster-config ConfigMap — repoURL, targetRevision, rhoaiChannel, rhoaiOverlay
  4. AppProjects — platform (operators/instances) + usecases (models/services)
  5. 4 ApplicationSets — auto-discovery engines for operators, instances, models, services
  6. rhoai-dsc Application — separate from AppSet (Replace sync + status ignore + retry config)
  7. gitops-controller — self-management at wave 10 (ServerSideApply, last to sync)

CRD timing: The bootstrap uses an until loop because the ArgoCD CRD isn't immediately available after the GitOps operator is installed. In our deploy, it succeeded on attempt 3 (10s sleep between retries).

"This is the moment of truth. One command: oc apply -k bootstrap/overlays/default. After this, you never run oc apply again." "Seven layers deploy in sequence. First, the GitOps Operator subscription — that installs ArgoCD. Then the ArgoCD instance itself, configured with Helm and Kustomize rendering, plus custom health checks that understand DSC and DSCI CRDs." "Next, the cluster-config ConfigMap with your 4 fields. Then AppProjects — we use two: 'platform' for operators and instances, 'usecases' for models and services. This gives you RBAC separation." "Then the 4 ApplicationSets — these are the auto-discovery engines. The rhoai-dsc Application deploys separately because it needs special handling: Replace sync strategy, status field ignoreDifferences, and a retry configuration with backoff." "And finally, gitops-controller at wave 10 — this is ArgoCD managing its own ArgoCD instance using ServerSideApply. It must be last to avoid a self-modification loop during bootstrap." "In practice, the ArgoCD CRD isn't immediately available after the GitOps operator installs. Our bootstrap script uses a retry loop — in our deployment, it succeeded on attempt 3 with a 10-second sleep between retries." --- pause --- "Now let me show you the operator dependency chain that ArgoCD has to orchestrate."

SECURITY

Secret Management Pattern

Never commit real credentials to Git. Three layers ensure secrets are safe and ArgoCD doesn't revert them.

Prune=false annotation on the Secret prevents ArgoCD from deleting it. ignoreDifferences prevents ArgoCD from reverting the real value back to the placeholder.

"Rule number one of GitOps: never commit real credentials to Git. But RHOAI needs a database connection URL for MaaS. How do you square that?" "Three layers." "Layer 1: Git. The repo contains a placeholder YAML — it's a real Kubernetes Secret object, correct namespace, correct key, but the value is literally the string REPLACE_ME. ArgoCD applies this and creates the Secret structure on the cluster." "Layer 2: ArgoCD. The instances ApplicationSet has ignoreDifferences configured for Secret objects on /data and /stringData jsonPaths. This tells ArgoCD: 'I know the cluster state differs from Git for these fields. Don't revert it. Don't flag it as OutOfSync.'" "Layer 3: On-cluster. An operator or administrator runs oc patch to set the real database connection URL. ArgoCD sees the diff, ignores it per configuration, and the MaaS API pod picks up the real secret and starts successfully." --- pause --- "Long-term, the External Secrets Operator is already deployed in the cluster. It can sync secrets from HashiCorp Vault, AWS Secrets Manager, or Azure Key Vault directly into Kubernetes Secrets. The dashed box on the diagram shows this future state — it's ready to configure." IF SOMEONE ASKS: "Why not use SealedSecrets?" — "SealedSecrets work too, but External Secrets Operator gives you runtime rotation and multi-backend support.
